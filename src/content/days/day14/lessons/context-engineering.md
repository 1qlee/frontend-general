## Why interviewers ask about this

Once you've said "I use Claude Code", a good interviewer asks *how*: "What's in your CLAUDE.md?", "How do you handle a big refactor?", "What do you do when it goes off the rails?" They want to hear a **workflow**, not a feature list. They're also listening for whether you treat context deliberately. That's what separates people who get consistent results from people who get lucky.

**Context engineering** is deciding *what the agent sees, when, and how much of it*: which facts are always loaded, which are loaded on demand, which work is delegated to a separate context, and what gets thrown away. Prompt wording matters much less than that.

> [!INTERVIEW] Say it like this
> "Most of my leverage comes from context, not clever prompts. Stable project facts go in CLAUDE.md, occasional know-how goes in skills, repeated prompts become slash commands, anything that must always happen is a hook, and investigation goes to subagents so the main context stays clean. Then every task gets a specific prompt with acceptance criteria and a way to verify."

## Designing CLAUDE.md

`CLAUDE.md` is loaded into context at the start of every session. That makes it powerful (Claude follows the team's rules without being told) and expensive (every line costs context, in every session, for everyone). Design it like a high-traffic API: small, stable, reviewed.

### What belongs and what doesn't

| Belongs in the project CLAUDE.md | Belongs somewhere else |
|---|---|
| Exact commands: dev, test (single run), single-file test, typecheck, lint, codegen | Long how-to guides needed only for some tasks → a **skill** |
| Architecture in 5–10 lines: where state lives, data fetching, routing, folder layout | Full API docs or the whole style guide → link to them, or a skill |
| Conventions that differ from the defaults (named exports, `interface` for props, RTL queries by role) | Things the linter/formatter already enforces → let the **hook/linter** do it |
| Gotchas: "React 19: no `forwardRef` needed for new components", "never import from `@/legacy`" | Personal preferences ("answer tersely") → **`~/.claude/CLAUDE.md`** |
| Explicit don'ts: no new dependencies without asking, never edit `src/generated/**` | Hard rules that *must* hold → **permissions/hooks** (CLAUDE.md is advisory) |
| Definition of done: "typecheck + tests pass; new UI has a test" | Secrets, tokens, internal URLs with credentials → **never** |

A good team file for a React + TypeScript app is often 30–60 lines:

```md
# Storefront web app

React 19 + TypeScript (strict) + Vite. Server state: TanStack Query. UI state: local state / Zustand.
Routing: React Router (file per route in src/routes). Design system: @acme/ui (see packages/ui).

## Commands
- `npm run dev` — dev server · `npm run typecheck` — tsc
- `npm test -- --run` — all unit tests once · `npx vitest run path/to/file` — one file
- `npm run codegen` — regenerate src/generated from the OpenAPI spec (never edit src/generated by hand)

## Conventions
- Named exports; props typed with `interface`; no `any` (use `unknown` and narrow).
- Use @acme/ui components before writing new primitives. Accessible by default: semantic HTML first.
- Tests: Testing Library, queries by role/label, user-event. No snapshot-only tests.

## Don'ts
- Don't add dependencies without asking. Don't modify tests to make them pass.
- Don't touch src/legacy (frozen; being replaced).

## Done means
`npm run typecheck` and `npm test -- --run` pass, and new behaviour has a test.
```

Two structural tools keep it small:

- **Imports:** a line like `@docs/architecture.md` includes that file. Use them to compose, not to dump everything in. Imported content costs context too.
- **Subdirectory `CLAUDE.md` files** are pulled in when Claude works with files in that directory. In a monorepo, `packages/ui/CLAUDE.md` can hold design-system rules that the checkout app never needs to pay for.

### Keeping it current

Treat `CLAUDE.md` like code: it lives in the repo, changes go through PRs, and it has owners.

- **Add a line when the agent makes the same mistake twice.** That's the highest-value signal you'll get about missing context.
- **Delete lines that no longer pay.** If the linter enforces it, or nobody's hit the problem in months, cut it.
- **Update it in the same PR** that changes a command, a folder layout or a convention. A stale `CLAUDE.md` is worse than none, because it creates stale assumptions with authority.
- Start from `/init` (it drafts one from the repo), then rewrite by hand. `/memory` opens memory files for editing.

> [!MISTAKE]
> Writing CLAUDE.md as an essay ("We value clean code and craftsmanship…"). The model can't act on values. It can act on commands, file paths, named patterns and explicit don'ts.

## The memory & settings hierarchy

Two parallel hierarchies: **memory** (instructions, `CLAUDE.md`) and **settings** (permissions, hooks, environment, `settings.json`).

| Memory layer | Location | Who it's for |
|---|---|---|
| Organisation policy | Managed by your organisation | Everyone; can't be overridden |
| User | `~/.claude/CLAUDE.md` | You, in every project (personal style, your shortcuts) |
| Project | `./CLAUDE.md` or `./.claude/CLAUDE.md` (checked in) | The whole team |
| Subdirectory | e.g. `packages/ui/CLAUDE.md` | Loaded when Claude works in that directory |

| Settings layer | Location | Shared? |
|---|---|---|
| Organisation-managed | Managed by your organisation | Overrides everything |
| User | `~/.claude/settings.json` | Personal, all projects |
| Project | `.claude/settings.json` | Checked in, whole team |
| Project-local | `.claude/settings.local.json` | Personal, git-ignored |

Rules to remember: organisation-managed settings override all; **deny wins over allow**; between the other layers, more specific generally beats more general (local over project over user), but check the exact precedence for your version (verify). Memory files don't override each other the same way. They're all loaded, so contradictory instructions across layers are a bug you should fix.

## Choosing the mechanism

The most common design question: *"Where should this live?"*

| You need… | Use | Loaded / runs | Enforced? | Frontend example |
|---|---|---|---|---|
| Always-true project facts | **CLAUDE.md** | Every session | No (advisory) | Commands, where server state lives, "never edit src/generated" |
| Know-how needed only for some tasks | **Skill** (`.claude/skills/<name>/SKILL.md`) | Name + description up front; body when relevant | No | "How we build forms with @acme/ui + zod", "Writing Storybook stories" |
| A prompt you trigger repeatedly | **Slash command** (`.claude/commands/<name>.md`) | When you type `/name` | No | `/new-component Tooltip`, `/a11y-check src/components/Menu.tsx` |
| A separate worker with a clean context | **Subagent** (`.claude/agents/<name>.md`) | When delegated | No, but tool access can be restricted | `react-reviewer`, `a11y-auditor`, "explore how auth works" |
| Something that must *always* or *never* happen | **Hook** (settings `"hooks"`) | On the event, every time | **Yes** | Prettier after every edit, block lockfile edits, `tsc` after edits |
| A new capability or data source | **MCP server** | Tool definitions every session | n/a | Playwright browser, Chrome DevTools traces, Figma design context |
| A hard boundary on what's allowed | **Permission rules** | Every tool call | **Yes** | Deny `Read(./.env)`, allow `Bash(npm run test:*)` |

Three questions resolve most cases:

1. **Must it happen every time, regardless of what the model decides?** → hook (or permission rule). Anything advisory will eventually be skipped.
2. **Is it needed in every session?** → `CLAUDE.md`. Only sometimes → skill (progressive disclosure keeps it out of context until it matches).
3. **Would doing it pollute the main context, or does it need a fresh, unbiased view?** → subagent.

Commands and skills overlap. Recent versions treat commands as a simple kind of skill, and `.claude/commands/` files keep working (verify for your version). Use a command when *you* decide when it runs. Use a skill when you want Claude to pick up the know-how automatically from its description.

## Core workflows

These are the patterns you practised in the daily labs, collected into one set. Pick by task shape.

### 1. Explore → plan → code → commit (the default)

1. **Explore:** "Read the files involved in X and explain how it works. Don't write code yet." (Or delegate to a subagent if it's broad.)
2. **Plan:** switch to plan mode (Shift+Tab, or `claude --permission-mode plan`) and ask for a plan with files, steps, risks and tests. Push back on the plan; this is the cheapest moment to change direction.
3. **Code:** implement step by step, verifying as you go.
4. **Commit:** review the diff, commit with a good message, and open a PR.

Skipping straight to "code" is the most common cause of a wrong-but-confident implementation.

### 2. Test-driven development

Write tests from the spec → run them and **confirm they fail** → commit the tests → implement until they pass **without modifying the tests** → review. Committing the tests first turns them into a fixed target, and makes any later test change visible in the diff.

### 3. Visual iteration

Give a mock or screenshot → implement → screenshot the result (Playwright MCP or manually) → compare → iterate 2–3 times. Name the differences you care about explicitly ("spacing between items is 8px in the mock, yours is 16px"). "Make it look like the mock" is too vague.

### 4. Spec-first features in vertical slices

For anything bigger than an afternoon: write a short spec (problem, behaviour, edge cases, a11y requirements, out of scope, acceptance criteria), then have the plan split it into **vertical slices**. Each slice is a thin, end-to-end, shippable piece with its own tests ("palette opens and closes with focus management" before "fuzzy filtering"), not horizontal layers ("all the types, then all the hooks, then all the UI"). Slices keep each context small, each diff reviewable, and each commit green.

### 5. Writer / reviewer with a fresh context

The session that wrote the code is biased toward it, because its context is full of its own reasoning. Review with a **clean context**: a second session, a reviewer subagent, or `/review` on the PR. Give the reviewer the diff and the spec, not the writer's conversation.

### 6. Parallel worktrees

Independent tasks can run at the same time in separate git worktrees, so the sessions don't trample each other's files:

```bash
git worktree add ../fe-gym-e2e -b chore/e2e-tests
cd ../fe-gym-e2e && claude
```

Rule of thumb: parallelise tasks that touch **different files** (tests for module A while you build feature B). Merging two agents' overlapping edits by hand costs more than doing them in sequence.

### 7. Headless fan-out for large migrations

For a mechanical change across many files (class components → function components, Enzyme → Testing Library, Jest → Vitest), one interactive "convert everything" session will drown in context. Fan out instead: **one small, verifiable task per `claude -p` run**, with restricted tools.

```bash
# 1. Build the task list (cheap, deterministic)
grep -rl "extends React.Component" src --include='*.tsx' > notes/migration-todo.txt

# 2. Pilot on 3 files first, read every diff, refine the prompt. Then run the rest.
mkdir -p notes/migration-logs
while read -r file; do
  claude -p "Convert $file from a class component to a function component with hooks.
Keep its props, behaviour and exports identical. Do not modify any other file or any test.
Done means: npx tsc --noEmit passes and its tests pass." \
    --allowedTools "Read,Edit,Bash(npx tsc:*),Bash(npx vitest:*)" \
    --max-turns 20 --output-format json > "notes/migration-logs/$(basename "$file").json"

  # 3. Verify independently; don't take the agent's word for it
  if npx tsc --noEmit && npx vitest run "${file%.tsx}"; then
    git add -A && git commit -qm "refactor: convert $(basename "$file") to a function component"
  else
    git checkout -- . && echo "$file" >> notes/migration-failed.txt
  fi
done < notes/migration-todo.txt
```

What makes this professional rather than reckless: a **pilot** before scaling, **restricted tools** per run, a **turn cap**, **independent verification** by the script (not the agent's self-report), **one commit per file** (easy to review, bisect and revert), a **failure list** for a human to handle, and running it on a branch, ideally in a worktree or container. The JSON logs are also data: today's second exercise summarises a run log like this.

> [!AGENT] Codemods first
> If a deterministic codemod can do 80% of a migration, run it first and use the agent for the remaining 20% that needs judgement. Agents are expensive and probabilistic; codemods are cheap and exact.

## Prompt anatomy for code tasks

Vague prompts get generic code. A strong task prompt has five parts:

| Part | Question it answers | Example |
|---|---|---|
| **Goal** | What outcome, for whom? | "Add client-side sorting to DataTable" |
| **Context / files** | Where should it look? What exists already? | `@src/components/DataTable/DataTable.tsx`; reuse `compareValues` in `src/lib/sort.ts` |
| **Constraints** | What must not change? | No new deps; props stay backward compatible; don't touch other components |
| **Acceptance criteria** | How will we know it's right? | Cycle asc → desc → none; `aria-sort` reflects state; nulls sort last; stable |
| **Verification** | What command or check proves it? | "Write failing tests first; done = `npx vitest run src/components/DataTable` + `npm run typecheck` pass; paste the output" |

Put together:

```text
Goal: add client-side sorting to DataTable: clicking a column header cycles ascending → descending → unsorted.

Context: @src/components/DataTable/DataTable.tsx and DataTable.test.tsx. Column definitions are in
src/components/DataTable/types.ts. Reuse compareValues from src/lib/sort.ts.

Constraints: no new dependencies; DataTable's public props stay backward compatible; sort controls are
<button>s inside the <th>, with aria-sort on the sorted <th>. Don't modify other components.

Acceptance criteria: the cycle above; aria-sort is "ascending"/"descending" on the sorted column;
sorting is stable; null values sort last in both directions.

Verification: first write failing tests for each criterion and show them to me before implementing.
Done = `npx vitest run src/components/DataTable` and `npm run typecheck` pass. Paste the output.
```

It takes two minutes to write, and it saves the twenty minutes you'd otherwise spend correcting a confident wrong guess.

## Context hygiene

| Habit | When | Why |
|---|---|---|
| `/clear` | Between unrelated tasks; after a long debugging detour | Fresh context: no stale observations, abandoned approaches or old errors |
| `/compact <focus>` | Mid-task when the window is filling but you need continuity | Summarises and frees space; focus instructions keep what matters |
| `/context` | When quality drops or before a big task | See what's eating the window (MCP tools? huge file reads?) |
| Checklist / scratchpad file | Any multi-step task | Durable state that survives `/clear` and compaction; the agent ticks items off |
| Subagents for investigation | "Find all…", "how does X work", reviews | Only the summary returns to the main context |
| Esc, then redirect | The moment it heads the wrong way | Course-correcting early is cheap |
| Esc Esc / `/rewind` | It went down a wrong path several steps ago | Restores the conversation and Claude's edits to a checkpoint |
| `claude -c` / `claude -r` | Picking work back up | Continue the latest session, or choose an older one |

A reliable rhythm for a long task: plan into `notes/<task>-plan.md` → implement one slice → verify → commit → have the agent tick the checklist → `/clear` → "Read notes/<task>-plan.md and continue with the next unchecked item."

> [!MISTAKE]
> Fighting a degraded session for another hour. When a session has gone bad (repeated mistakes, contradictions, re-introducing rejected ideas), it's almost always faster to write down the current state, `/clear`, and restart with a focused prompt.

## Key takeaways

- **Context engineering**, meaning what's loaded, when, and how much, matters more than prompt wording.
- `CLAUDE.md`: short, concrete, checked in, reviewed; commands, architecture, conventions, gotchas, don'ts. Add a line when a mistake repeats; delete lines that don't pay.
- Memory layers are all loaded; settings layers have precedence (org-managed overrides all, deny wins).
- **Where it lives:** always-true facts → CLAUDE.md; sometimes-needed know-how → skill; repeated prompt → command; clean separate context → subagent; must-always/never → hook or permission; new capability → MCP.
- Workflows: explore → plan → code → commit; TDD with committed tests; visual iteration; spec-first vertical slices; writer/reviewer with fresh context; worktrees for parallel work; headless fan-out with pilots, restricted tools and independent verification.
- Prompt anatomy: **goal, context, constraints, acceptance criteria, verification.**
- Hygiene: `/clear` often, `/compact` with focus, `/context` to diagnose, files for durable state.
